`scripts/02_inspect.py` and `scripts/02b_verify_download.py`, outputs saved in `results/`),

### 3.1 Bands, dtype, units (measured, all 446 chips)

- `S1Hand`: every file is `(2 bands, float32, 512 x 512)`; band 0 = VV, band 1 = VH (band order
  stated by the README; consistent with the value ranges). **Units are dB** (stated by README;
  measured values are in a dB-like range, see 3.3). No conversion is applied.
- `LabelHand`: every file `(1, int16, 512, 512)`, values -1 (no data), 0 (not water), 1 (water).
- `JRCWaterHand`: `(1, uint8, 512, 512)`; `S1OtsuLabelHand`: `(1, int16, 512, 512)` with values
  {0, 1} (measured on one chip).
- CRS EPSG:4326; pixel size 8.98e-5 degrees, about 10 m (measured from the geotransform).

## 4. What the labels mean

**Question from the brief:** does `LabelHand == 1` mean "flood only" or "all water including
permanent water"?

**Measured on one chip** (`Ghana_103272`), `LabelHand` against `JRCWaterHand`:

| | JRC = not permanent water | JRC = permanent water |
|---|---|---|
| Label = not water | 257,654 | 57 |
| Label = water | 1,183 | 375 |

375 pixels are labelled water and are also JRC permanent water. **Measured over all 446 chips**,
3,062,228 of 10,705,605 labelled-water pixels (**28.60%**) coincide with JRC permanent water.
So `LabelHand` is all water (permanent + flood), not flood-only. The paper (stated, section 3.2)
likewise reports separate metrics for flood-water and permanent-water pixels.

**Same pixel grid** (measured, all 446 chips): `LabelHand` and `JRCWaterHand` match in CRS,
size (512 x 512) and pixel size on every chip. Their affine origins differ by about 1e-11
degrees (about 1e-6 m; a pixel is 8.98e-5 degrees). That is floating-point representation noise
from separate exports, not misalignment. An exact-equality first attempt flagged it; the check
now allows 1e-6 degrees (about 0.11 m, about 1/90 of a pixel), which cannot hide a real shift.

**Definitions fixed on 2026-09-20 before any score existed** (full text in
`results/evaluation_protocol.md`): headline metric is flood-only, with the JRC permanent-water
mask applied to **both** prediction and truth; NaN and label -1 pixels are ignored, never counted
as "not flood". All-water is the secondary metric. Pooled counts: all-water 10,705,605
pixels, flood-only 7,643,377, JRC removes 3,062,228.

## 6. Events covered, and the Ghana question

The 446 hand-labelled chips come from **11 events**. The event metadata GeoJSON lists **12**
events: it also lists Colombia (`val_chip: 0`, i.e. no hand-labelled chips), which is therefore
not in our data. The chip files call one event "Mekong"; the metadata calls the matching event
"Cambodia". This is **confirmed, not assumed**: chip `Mekong_16233`'s own GeoTIFF bounds (read

almost certainly not the same setting as the Odaw basin (land cover per chip was not measured).
Ghana in the benchmark does not close the Accra domain gap.

## 7. Land cover and domain gap

- **Stated** by the authors (CVPRW 2020 paper, limitations), verbatim:
  > "Our validation dataset does not include any urban flood events, in part because Sentinel-1
  > algorithms often struggle to map floods in urban areas."
- **Stated**: events were selected from the Dartmouth Flood Observatory database and required
  Sentinel-1 plus coincident Sentinel-2 imagery.
- **Not measured**: the land-cover type of the chips. Calling the benchmark mostly
  rural/riverine is my **assumption**, supported only by the authors' statement above.
  Accra is urban, so a domain gap should be assumed and stated in every Accra output.

## 8. Pre-event imagery

No pre-event Sentinel-1 layer exists in the bucket folders or in the README layer table (one
`S1Hand` file per chip), and the metadata gives a single `s1_date` per event (**stated** and
**measured**). So change detection is not possible on this benchmark; only single-image methods
apply.

## 9. Reference layers provided by the dataset

- `JRCWaterHand`: per-chip permanent-water mask, Landsat-derived (stated). Used for the
  flood-only metric, and the same idea is reusable for the Accra permanent-water mask.
- `S1OtsuLabelHand`: the dataset's own Otsu-on-VH labels (values {0, 1}; on `Ghana_103272`
  2,454 water pixels of 262,144, measured). Used only as a labelled sanity-check comparison.
  Our B2 is our own Otsu implementation under our preprocessing and protocol.

## 10. Download integrity: how "all files valid" was decided

Script `scripts/02b_verify_download.py`, output `results/download_verification_output.txt`
(**measured**). A file is valid only if all of these hold: (1) it exists and is non-zero; (2)
rasterio opens it and reads the whole array (a truncated GeoTIFF raises); (3) it is 512 x 512
and all files in a folder share one (band count, dtype); (4) its byte size equals the size of the
same object in the bucket listing.

| Folder | Files on disk | Pass all 4 criteria | (bands, dtype) | Local bytes = bucket bytes |
|---|---|---|---|---|
| `S1Hand` | 446 | 446 | (2, float32) | 729,495,935, equal |
| `LabelHand` | 446 | 446 | (1, int16) | 2,553,880, equal |
| `JRCWaterHand` | 446 | 446 | (1, uint8) | 515,103, equal |
| `S1OtsuLabelHand` | 446 | 446 | (1, int16) | 1,712,242, equal |

Total 734,277,160 bytes locally and in the bucket listing. That is **734.3 MB** in decimal units
and **700.3 MiB** in binary units. The earlier "705M" was `du -sh`, which reports MiB of disk
blocks (disk-block accounting); `du --apparent-size` gives 701M, which is 700.3 MiB of data plus the
split CSVs and about 0.4 MB of helper files in the folder. The 705 vs 734 gap is therefore a unit
and block-accounting difference, not compression variance as I said before.

History: the network was unreliable, and parallel `curl` left truncated and 0-byte files while
reporting success. `scripts/_verify_and_repair_downloads.py` (criteria 1 and 2 only) found 293
missing or corrupt files in its first pass and 0 in its second; `02b_verify_download.py` then
applied all four criteria.

## 11. Decisions taken (2026-09-20)

1. NaN imagery pixels are masked in every metric, as well as label -1; chips with no valid pixels
   are dropped (six chips, listed in 3.2); k-means is fitted on valid pixels only; NaN is handled
   before SLIC and re-masked afterwards.
2. dB clipping is a tuned preprocessing option chosen from fixed ranges in
   `configs/config.yaml` on tuning chips only, and applied to the threshold baselines too.
3. Primary evaluation is leave-one-event-out over all 11 events; the official split is
   secondary. Details in `results/evaluation_protocol.md`.
