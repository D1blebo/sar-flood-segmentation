# Evaluation protocol

Written on 2026-09-20, **before any method has been scored on any chip**. Every rule below is
either taken from the project brief (`CLAUDE.md`), from decisions the project owner gave in the
conversation, or is a choice I made and label **[my choice]** so it can be challenged. Candidate values live in `configs/config.yaml` (sha256 at time of writing is at the
end of this file). Chosen values are written later to `results/frozen_config.yaml` and are never
edited into the config.

## 1. Pixel definitions

For a chip, let `VV`, `VH` be the Sentinel-1 bands (dB), `L` the hand label (`-1` unlabelled,
`0` not water, `1` water) and `J` the JRC permanent-water mask (`1` permanent water).

- **Image-valid** pixel: `VV` and `VH` are both finite (not NaN).
- **Label-valid** pixel: `L != -1`.

### Primary metric: flood-only

- Evaluation domain `D_flood = image-valid AND label-valid AND (J == 0)`.
- Truth flood = `L == 1` inside `D_flood`.
- Predicted flood = method output `== 1` inside `D_flood`.
- The JRC mask is therefore applied to **both** prediction and truth: permanent-water pixels are
  removed from the domain, so they can be neither a true positive, a false positive, a false
  negative nor a true negative. (Zeroing both masks inside `J == 1` gives identical IoU, F1,
  precision and recall, because true negatives do not enter those four; it differs only in the
  denominator of the flood-free false-positive rate, which is defined on `D_flood` only.)
- NaN pixels and label `-1` pixels are **ignored**. They are never counted as "not flood".

### Secondary metric: all-water

- Domain `D_all = image-valid AND label-valid`; truth = `L == 1`; no JRC mask.

The methods themselves never see `L` or `J`. The oracle diagnostic (section 5) sees `L`, and is
never used for a reported headline number.

## 2. Chip rules

- **Exclusion:** a chip with **zero** pixels in the relevant domain is dropped from that metric
  (`D_flood` for the primary metric, `D_all` for the secondary). The rule is identical for every
  split, every method and every evaluation protocol. The exclusion list is generated by
  `scripts/02_inspect.py` (`results/data_inspection_output.txt`), not written by hand.
- **Flood-free chips** (domain non-empty, zero truth-flood pixels): per-chip IoU/F1/recall are
  undefined and are **not** averaged. They are reported separately as a false-positive rate,
  `FP / (FP + TN)` on `D_flood`.
- **Strata** by flood fraction `= truth-flood pixels / |D_flood|`: `none` (0), `<5%`, `5-30%`,
  `>30%` (bins from the brief; `none` is the false-positive-rate group).

## 3. Metrics

From per-chip counts TP, FP, FN, TN inside the domain:

- IoU = TP / (TP + FP + FN); precision = TP / (TP + FP); recall = TP / (TP + FN);
  F1 = 2TP / (2TP + FP + FN).
- A metric whose denominator is 0 is **undefined (NaN)** and reported as undefined, never
  silently replaced by 0 or 1.
- **Pooled:** sum TP, FP, FN over chips, then compute the metric. **Per-chip:** compute per chip,
  then average over chips where it is defined.
- Overall accuracy is not a headline number (flood is a minority class).
- **Uncertainty:** bootstrap over **chips** (1000 resamples, seed from config, percentile 95% CI),
  recomputing the pooled and the mean-per-chip statistic on every resample. For per-event results
  the resampling is within the event.

## 4. Preprocessing (identical for every method, including the threshold baselines)

Order: keep the NaN mask, clip, median filter, method.

- **NaN:** the NaN mask is remembered and re-applied to every method output (predicted flood is
  `False` on NaN pixels). K-means is fitted on valid pixels only. Before SLIC, NaN is filled with
  the chip's valid median so no NaN reaches the C code, SLIC is run without its `mask` argument
  (see Amendment 1, item 3), and segments are re-masked to "invalid" afterwards.
- **Clip (fixed ranges, in the config, chosen before scoring):** `none`, `wide`
  (VV -40..10, VH -45..0 dB), `medium` (VV -30..5, VH -35..-5), `narrow` (VV -25..0, VH -30..-8).
  Which option is used is a tuned hyperparameter selected on **tuning chips only**. The number of
  pixels each range changes is reported by `scripts/02_inspect.py`. The same clip is applied to
  B1 and B2. Note for SLIC: skimage rescales the image to [0,1] using the min/max of the unmasked
  pixels, so extreme outliers shrink the useful range; clipping therefore also changes SLIC.
- **Speckle:** none or a NaN-safe median filter with window 3, 5 or 7 (NaN is filled with the chip
  median, filtered, then restored to NaN). The median is rank-based, so filtering in dB or in linear
  power gives the same result.
- **Units:** data are already in dB (measured, `results/data_inspection_report.md`), so no
  conversion is applied.

## 5. Methods and the cluster-to-water rule

All methods implement `predict(vv, vh) -> bool mask` (False on NaN).

- **B1** fixed threshold on VV (water if `VV < t`), `t` tuned on tuning chips.
- **B2** Otsu threshold computed per chip on valid pixels, run separately on VV and on VH.
  Known to degrade when water is a small share of the chip.
- **M1** pixel-level k-means on (VV, VH), k in {2,3,4,5}.
- **M2** SLIC superpixels then k-means on per-segment features, k in {2,3,4,5}; features
  {mean VV; mean VV+VH; plus std of each; plus mean(VV-VH)}; `n_segments`, `compactness` tuned.
- **Rule (fixed a priori):** the cluster whose pixels have the **lowest mean VV** is water. Ties go
  to the lowest cluster id.
- **Oracle diagnostic:** the single cluster with the highest IoU against truth. Diagnosis only:
  never a reported headline result. The gap rule-vs-oracle separates rule error from clustering
  error.
- `S1OtsuLabelHand` (the dataset's own Otsu-on-VH layer) is used **only** as a labelled sanity-check
  comparison. It is not baseline B2.

## 6. Evaluation design

### Primary: leave-one-event-out (LOEO), all 11 events, Bolivia included

For each event E: the **tuning set** is every hand-labelled chip of the other 10 events (whatever
their official split); the **evaluation set** is every chip of E. Hyperparameters are selected on the
tuning set only, then E is scored once. Report per-event results with bootstrap CIs, plus a summary
over events (pooled, and macro-average of per-event scores). Small events (Bolivia 15 chips,
Nigeria 18) will have wide intervals and this is reported, not hidden.

### Secondary: official split

Tune on the official **validation** split only, freeze the choice to `results/frozen_config.yaml`,
score the official **test** split once, and score the held-out Bolivia chips separately with the same
frozen config. LOEO folds use official test chips of other events as tuning data, so LOEO configs are
never reused for this analysis; the two analyses are separate and are not treated as independent
evidence.

### Selection rule **[my choice]**

Select by **mean per-chip flood-only IoU over tuning chips that have at least one truth-flood pixel**
(brief: "select by mean flood IoU"). Ties: higher pooled IoU, then the earlier candidate in config
order. Weakness, stated up front: flood-free tuning chips do not enter this criterion, so
over-prediction there is only visible in the reported false-positive rate.

### Leakage guard

An automated test fails if any chip ID is in both the tuning set and the evaluation set, for the
official protocol and for every LOEO fold, and if a held-out event has any chip in its tuning set.

### Cost control

SLIC segmentations are cached on disk keyed by (chip, preprocessing options, `n_segments`,
`compactness`); they do not depend on k or on the feature set. Per-chip confusion counts are cached
per configuration, so one pass over all 446 chips per configuration serves all 11 LOEO folds (each
fold just sums a different subset). Tuning uses a staged or random search sized to about 45 minutes
per run on the laptop, measured by timing one configuration first.

### Accra frozen configuration **[proposal, needs approval before Stage 4]**

Accra is outside the benchmark, so the configuration for the demonstration can be selected with the
same rule on all 446 chips pooled without leaking into any benchmark score. Not applied until you
approve.

## 7. What is reported, in order

1. Exclusion list and counts (data facts).
2. Clip-range pixel-change counts.
3. Only then, scores: LOEO per event (primary), official split (secondary), each with flood-only
   (headline) and all-water (secondary), pooled and per-chip, bootstrap CIs, by stratum, rule vs
   oracle, and the `S1OtsuLabelHand` sanity comparison.

Every number in the final report must come from a script run and be labelled measured; rules and
literature claims are labelled assumed.

## Amendment 1 (2026-09-20, after the Stage 2 smoke test, before any tuning or test scoring)

The only scores that existed at this point were a smoke test on 6 official-validation chips with
untuned nominal parameters (`results/stage2_smoke_output.txt`); nothing was tuned or selected from
them. Two things were learned and are written down here rather than edited silently into the text
above. Neither changes a definition in sections 1 to 4.

1. **Rule-vs-oracle gap is reported on mean per-chip flood-only IoU, not pooled IoU.** Per chip the
   oracle can never score below the rule (it searches every cluster, including the rule's), and this
   was verified chip by chip. Pooled, the oracle can score *lower*: on a tiny-flood chip the
   best-IoU cluster can be a near-whole-chip cluster (per-chip IoU about 0.003, but hundreds of
   thousands of false-positive pixels), which dominates a pooled sum. Pooled oracle numbers are not
   reported as a "ceiling".
2. **Search cost (measured on this laptop, one chip):** SLIC costs about 0.4 to 0.5 s per chip
   whatever `n_segments` is; pixel k-means about 0.5 to 0.7 s per chip; one cached M2 k-means pass
   about 0.03 s per chip. One M2 segmentation configuration over all 446 chips is therefore about
   3.5 to 4 minutes, and the full M2 menu (4 clips x 4 median windows x 4 `n_segments` x 4
   `compactness` = 256 segmentation configurations) would take about 14 hours, so the tuning search
   is staged or random, about 12 segmentation configurations per 45-minute run. Cached segmentations
   are about 19 KB each (compressed), so even the full menu would be about 2 GB.
3. **SLIC is run without its `mask=` argument.** The first draft said the valid mask would be passed
   to SLIC. Measured on one real chip, the masked path took 0.7 to 8.4 s per chip (200 to 2000
   segments) against about 0.35 s unmasked, because its seeding runs a k-means over the pixel
   coordinates. NaN is instead filled with the chip's valid median before SLIC and re-masked after,
   as originally instructed. Segments that mix real and filled pixels use only their valid pixels
   for features.

## Amendment 2 (2026-09-20, before any tuning and before any test scoring)

Requested after review of the config, protocol, `cluster_rule.py` and the smoke output. Nothing here
was chosen from scores: the only scores that exist are the 6-chip validation smoke test. Candidate
values are in `configs/config.yaml`, whose new sha256 is at the end of this file.

### A2.1 Abstention guard (new candidates B2g, M1g, M2g; the plain rule stays the a-priori method)

- **Rule:** a predicted water region (a cluster, or the Otsu-dark side) counts as water only if its
  **mean VV is below a ceiling**; otherwise the chip gets **no predicted flood**. For a cluster method
  the region is exactly the chosen cluster, so this is the cluster's mean VV.
- **Ceilings:** a short list fixed in the config before any scoring, **-18, -15, -12 dB** (strict,
  moderate, permissive). Basis is radar physics, not scores, and it is **assumed** (general knowledge,
  not checked in this project): calm open water is roughly -20 dB VV or darker, and land is usually
  brighter than about -12 dB. Rough or wind-roughened water and flooded vegetation can be brighter,
  so the guard will sometimes abstain on real water; that recall cost is measured, not assumed away.
- **What it applies to:** B2 (VV and VH versions), M1, M2. B1 has no guarded variant (its threshold is
  already an absolute dB value). The ceiling is a hyperparameter of the guarded variants; "plain" means
  no ceiling. All variants of one configuration come from the same clustering, so they cost one run.
- **Oracle:** unchanged, defined on the plain cluster map (the guard does not affect it).
- **Reporting:** for **every** method and variant, flood-free false-positive fractions on the flood-free
  chips: the fraction of flood-free chips where any flood is predicted, and the pooled pixel
  false-positive rate `sum(FP) / sum(FP + TN)`, for flood-only (headline) and all-water.

### A2.2 Bootstrap

- **Summaries over events use a two-level bootstrap:** resample the 11 events with replacement, then
  resample chips with replacement within each sampled event, 1000 times, seed from the config,
  percentile 95% interval. The per-event statistic is computed on the resampled chips and the
  macro-average is the unweighted mean over the sampled events.
- **Reported:** the macro-average over the 11 events with this event-level interval, for both per-event
  statistics (mean per-chip flood-only IoU over chips with flood, and pooled flood-only IoU). The mean
  per-chip IoU is the headline **[my choice]** because it is the selection criterion. **[Superseded by Amendment 8, A8.1: the headline is pooled flood-only IoU.]**
- **Caveat, stated plainly:** per-event intervals (chips resampled within one event) **treat chips
  within an event as independent**. Chips from one flood event are spatially and radiometrically
  correlated, so these intervals **understate** the true uncertainty. The official-split intervals
  (chips resampled over a mix of events) carry the same caveat.

### A2.3 Search plan (declared before running)

A "tuning set" is one of the 11 leave-one-event-out folds or the official validation split. Per-chip
confusion counts are computed once per configuration and cached on disk; each tuning set just sums a
different subset of chips, and configurations that a tuning set needs but that are not yet cached
are computed on demand. Ranking everywhere is the selection rule of section 6 (mean per-chip
flood-only IoU over tuning chips with flood), applied per tuning set. Every configuration is scored
unguarded and at every ceiling. **[Ranking rule superseded by Amendment 3, A3.1: plain methods are ranked on
unguarded scores only.]**

| Stage | What varies | Methods | Notes |
|---|---|---|---|
| 1 | clip (4) x median window (4) = 16 preprocessing options | B1 (all thresholds valid under the clip), B2 (VV, VH), M1 at k=3, M2 at nominal SLIC (k=3, `n_segments` 500, `compactness` 0.05, features `vv_vh`) | Keep the **best two** preprocessing options per method and tuning set. B1 and B2 are exhaustive here and finish at this stage. |
| 2 | M1: k in {2,3,4,5}. M2: `n_segments` (4) x `compactness` (4) | on each method's best two preprocessing options | Clip and compactness are chosen **jointly**: skimage rescales each chip to [0,1] by its own min/max, and the clip changes that min/max, so both preprocessing options are carried through this stage, not just the first. |
| 3 | M2: k (4) x features (4) | on the best stage-2 configuration | Reads the cached segmentation; k-means only. |

**[Cost estimate below superseded by Amendment 3, A3.2.]** Estimated cost on this laptop (measured per-chip times from the smoke test, 4 workers): stage 1 is
16 x 446 chips x about 1.4 s = 2.8 h serial, about 45 min with 4 workers. Stage 2 is about 245 s per
(preprocessing, `n_segments`, `compactness`) over 446 chips serial, about 1 min with 4 workers; with
2 preprocessing options per tuning set the union over 12 tuning sets is probably 3 to 6 options, so
about 50 to 100 such configurations, 1 to 2 h. Stage 3 is about 1 min per configuration. Runs are
resumable and are executed in chunks of about 45 minutes or less.

### A2.4 Speed

- **Hardware (measured):** Intel i7-8665U, 4 physical cores / 8 threads, 15 GB RAM. Work is parallelised
  across chips with **4 worker processes**, each limited to one BLAS/OpenMP thread (`src/parallel.py`;
  a test checks parallel results equal serial results).
- **M1 subsample fit:** fit k-means on a random subsample of **50,000 valid pixels** (seeded), then assign
  all pixels to the nearest centre. Adopted only if `scripts/verify_speed_checks.py` passes this rule,
  fixed **before** it was run: on 20 official **train** chips x k in {2,3,4,5} x two preprocessing
  settings (no clip / medium clip + median 3), compared with the full fit and using no labels,
  **mean matched-partition agreement >= 0.99 and worst >= 0.95, and mean water-mask IoU >= 0.99 and
  worst >= 0.95**. Otherwise M1 keeps the full fit. The measured outcome is appended below.

### A2.5 Grid edges

- If the winner of a tuning set sits on the edge of a **numeric** grid, that grid is extended by one
  step **for that tuning set only**, using **that tuning set's data only** (so a held-out event can never
  influence its own grid), then the search is repeated on the new edge. At most 2 extensions per
  parameter **[my choice]**, to keep compute finite.
- One step: B1 threshold +/- 1 dB; median window +2 (7 to 9); `n_segments` x2 or /2; `compactness` x5 or
  /5; k +1 above 5 only (k is never extended below 2); ceiling +/- 3 dB. The clip option is categorical
  and is never extended.
- Every extension is logged as a dated entry in `results/grid_extension_log.md` (tuning set, parameter,
  old edge, new value), which is this protocol's log of extensions.
- **B1 thresholds** that predict nothing under a clip (t <= the clip's VV floor) are skipped
  (`b1_thresholds_for_clip`, tested).

### A2.6 Which VV the cluster rule receives

The rule (and the abstention ceiling) receives the **VV after the clip and the median filter**, i.e.
exactly the array the method clustered, not the raw VV. The oracle uses the same cluster map. This is
enforced in `src/evaluate.py` and by a test in which a raw-VV outlier would flip the rule's choice.

### A2.7 Measured outcomes of the speed checks (2026-09-20, `results/speed_checks_output.txt`)

- **M1 subsample fit: NOT adopted** (the rule declared in A2.4 fails). Over 160 comparisons (20 train chips,
  k in 2..5, two preprocessing settings) mean partition agreement was 0.963 (worst 0.499) and mean
  water-mask IoU 0.927 (worst 0.013). It is fine at k=2 (mean IoU 0.987 to 0.989, worst 0.93) and
  degrades with k (k=5: mean 0.82 to 0.90, worst 0.01 to 0.21): at higher k the rule can pick a
  different cluster from the subsample fit than from the full fit. It was also only 1.6x faster
  (95 s vs 60 s for 160 fits, one thread). `fit_subsample` therefore stays `null` in the config.
  Side observation, not a result: this instability suggests M1's water cluster at k >= 4 depends on
  the k-means initialisation, which is worth remembering when interpreting M1 at high k.
- **Parallel across chips:** 20 chips, M1 k=3 full fit: 12.1 s serial, 6.0 s with 4 workers (2.0x),
  7.5 s with 8 workers (slower, since 8 threads share 4 physical cores). Results were identical across
  worker counts. The 4-worker figure includes about 3 to 4 s of process start-up, so large batches
  should get closer to 4x, but that is **not yet measured**. **Correction to A2.3:** stage 1 is
  therefore estimated at about 45 to 85 minutes (not a flat 45), to be re-measured on the first real
  chunk. `compute.n_jobs` stays 4.

## Amendment 3 (2026-09-20, before any tuning and before any test scoring)

### A3.1 Plain and guarded variants are selected independently

This replaces the sentence in A2.3 that ranked every configuration "by its best ceiling", which would
have let the guard influence the plain rule's selection.

- **Plain methods (B1, B2-VV, B2-VH, M1, M2) are selected on their UNGUARDED scores only.** The guard
  never enters their ranking, at any stage.
- **Guarded variants (B2g, M1g, M2g) are separate methods with their own selection.** Their candidates
  are **(configuration, ceiling) pairs**, so the ceiling is chosen jointly with the configuration, at
  every stage: each stage keeps the best two preprocessing options for the guarded variant by the best
  (configuration, ceiling) score, and the final choice is one (configuration, ceiling) pair. The guarded
  variant's chosen configuration may therefore differ from the plain method's.
- Both use the same ranking criterion (mean per-chip flood-only IoU over the tuning set's chips with
  flood). A guarded and a plain candidate that share a configuration share one clustering, so the guard
  adds no clustering cost; it adds cost only where its selected configuration differs from the plain one.
- Each tuning set therefore freezes **nine** selections: plain B1, B2-VV, B2-VH, M1, M2, and guarded
  B2g-VV, B2g-VH, M1g, M2g (seven method families, as listed in the config's flood-free reporting).

### A3.2 Stage 2 when tuning sets pick different preprocessing options

- **Each tuning set (11 folds + the official validation split) ranks only within its own top two** options
  from stage 1, so its selection is exactly what a private search on its own data would give. Nothing
  from another tuning set can change it.
- **Compute is shared through the cache.** Stage 2 evaluates the **union**, over all 12 tuning sets and
  over the plain and guarded variants, of each method's top-two options: every distinct (method,
  preprocessing option) is run once over all 446 chips, stored, and read by every tuning set that
  needs it. (Each tuning set uses only its own chips' counts.)
- **What the union does to cost.** Per option in the union, one M2 stage-2 sweep (4 `n_segments` x 4
  `compactness`, 446 chips, 0.55 s per chip, serial) is about 65 min, and one M1 stage-2 sweep
  (3 new k values, 0.6 s per chip) about 13 min. Divide by the measured parallel speedup, 2.0x (the
  hoped-for 4x is unmeasured). Union size U per method is unknown until stage 1 finishes (**assumed**
  to be small because any two tuning sets share at least about 70% of their chips, but not
  guaranteed; the official validation split, with 86 chips, may differ most):

  | Union size U (per method) | M2 stage 2, 2x | M2, 4x | M1 stage 2, 2x | M1, 4x | M1 + M2, 2x | M1 + M2, 4x |
  |---|---|---|---|---|---|---|
  | 2 | 1.1 h | 0.5 h | 0.2 h | 0.1 h | 1.3 h | 0.7 h |
  | 4 | 2.2 h | 1.1 h | 0.5 h | 0.2 h | 2.7 h | 1.3 h |
  | 8 | 4.4 h | 2.2 h | 0.9 h | 0.4 h | 5.3 h | 2.7 h |
  | 16 (worst case) | 8.7 h | 4.4 h | 1.8 h | 0.9 h | 10.5 h | 5.3 h |

  So the earlier "1 to 2 h" was optimistic: it counted only M2, assumed 4x, and assumed 3 to 6 options.
  Corrected: stage 1 is about 40 to 75 min (16 options x 446 chips x about 1.25 s for B1, B2, M1, M2
  together, at 4x to 2x), and stage 2 is about 1 to 3 h if U is 3 to 6, more if the tuning sets disagree.
  Stage 3 stays about 1 min per configuration.
- **Checkpoint:** when stage 1 finishes I report, for every method and variant, the union size U and the
  projected stage-2 cost from measured per-chip times, and **wait for approval before starting stage 2**.
  I do not trim the union by any data-dependent rule of my own, because that would let one tuning set's
  data shape another's search.

### A3.3 Seed sensitivity of M1 at k = 4 and k = 5 (tuning chips only)

- **Design, fixed in `config.seed_sensitivity` before running:** M1 at k in {4, 5}; seeds
  **{42, 0, 1, 2, 3}** (42 is the config seed and the reference); 40 official **TRAIN** chips (seeded
  shuffle, chips with no valid pixel skipped); two preprocessing settings (no clip / median 0, and
  medium clip / median 3); `n_init` as in the config (3). No labels are used.
- **Measure:** for each (chip, preprocessing, k, seed other than the reference), the IoU between that
  seed's water mask (the a-priori rule's pick) and the reference seed's. The lowest-VV cluster is counted
  as **changed** if that IoU is below **0.95**. Reported per (preprocessing, k): the share of comparisons
  that changed, the number of chips with any change, and the median and worst IoU; also per seed.
- **What it is for:** it quantifies how much M1's result at high k depends on the k-means seed, so the
  size of the seed effect can be compared with differences between configurations. It triggers no
  automatic change; any consequence (more `n_init`, several seeds, or reporting seed variance) is put
  to the project owner. Its measured outcome is appended to this protocol after the run.

### A3.4 Tuning logs and held-out scoring are separate

- **Tuning logs show tuning-set metrics only**: aggregates over the chips of one tuning set, labelled
  with that tuning set. They never show a metric, or a per-chip number, for a held-out chip. The tuning
  code is handed only tuning chip ids.
- **Held-out scoring is a separate script** (`scripts/04_evaluate.py`, to be written in Stage 3), run
  **once**, and only **after every frozen per-tuning-set configuration exists** (11 folds and the
  official split); it refuses to start otherwise. It recomputes the held-out counts from the frozen
  configuration instead of reading per-chip counts from the tuning cache, and writes a lock file (hash of
  all frozen configurations) so a second run is refused unless the lock is deleted by hand and that
  deletion is logged here.
- The per-chip count cache used during tuning is never printed chip by chip.

### A3.5 Version control

`sar_flood/` was not a git repository of its own (it sits inside the home-directory repository of another
project, which is not touched). A repository was initialised in `sar_flood/` and `src/`, `configs/`,
`tests/` and this file were committed **before any tuning**; the commit hash is reported in the session
summary. Later edits to tracked files show up as diffs against that snapshot.

### A3.3 result (2026-09-20, `results/seed_sensitivity_output.txt`; measured, tuning chips only, no labels)

40 official train chips, seeds {42 (reference), 0, 1, 2, 3}, `n_init` 3, 640 comparisons. "Changed" means the
water mask has IoU < 0.95 with the reference seed's mask.

| Preprocessing | k | Comparisons changed | Chips with any change | Median IoU | Worst IoU |
|---|---|---|---|---|---|
| no clip, median 0 | 4 | 37 / 160 (23.1%) | 17 of 40 | 0.985 | 0.002 |
| no clip, median 0 | 5 | 60 / 160 (37.5%) | 26 of 40 | 0.969 | 0.000 |
| medium clip, median 3 | 4 | 30 / 160 (18.8%) | 19 of 40 | 0.984 | 0.678 |
| medium clip, median 3 | 5 | 56 / 160 (35.0%) | 26 of 40 | 0.968 | 0.000 |

Per non-reference seed, the water mask changed on 25.6% to 33.1% of comparisons. Reading: most comparisons
agree closely (median IoU about 0.97 to 0.99), but a heavy tail of chips gets a very different water mask
(worst IoU 0.000 to 0.002), and about one in five (k=4) to one in three (k=5) comparisons changes. So with a
single seed, M1's score at k >= 4 carries seed noise of unknown but non-trivial size, and selecting k or a
preprocessing option on one seed's scores can partly select noise. **Limitation of the measure:** it
counts a changed mask, and does not separate "the rule picked a different cluster" from "the same cluster
with a different boundary". No change to the plan was made from this; the options are put to the project
owner.

## Amendment 4 (2026-09-20, before any tuning and before any test scoring; written BEFORE the follow-up ran)

### A4.1 M1 seed follow-up: design and decision rule

**Why:** the first seed check (A3.3) found M1's water mask changes for 19% to 38% of comparisons at k = 4 and
5 with `n_init` = 3, and did not measure k = 3, on which Stage 1 depends.

**Design (config `seed_sensitivity_followup`, fixed before running).** Same 40 official TRAIN chips, same 5
seeds (42 as reference, 0, 1, 2, 3), same "changed" definition (water-mask IoU with the reference seed below

### A5.3 Stage 2 union: capped at 6 options

This replaces the uncapped union of A3.2 (its "each tuning set ranks only within its own top two" gets the fallback
below). Applied **per method variant** (M1, M1g, M2, M2g); B1 and B2 finish in stage 1.

1. From each of the 12 tuning sets, take that set's **top 2** preprocessing options for the variant (stage-1 ranking).
2. Rank the options by **how many tuning sets put them in their top 2** (descending); break ties by **mean rank over all
   12 tuning sets' full stage-1 rankings** (1 = best, ascending). Keep the **top 6**: this is the union.
3. **Fallback:** a tuning set whose top-2 options are not in the union uses its **own best-ranked options that are in the
   union** (up to two), so it still ranks only using its own data.
4. Each option in the union is computed once for all chips and cached; each tuning set reads only its own chips.
- **Known limitation (leakage path):** the union depends on every tuning set's stage-1 ranking, and each ranking is computed
  from data that include *other* folds' held-out events. So a held-out event's chips can, through the other folds' rankings,
  influence **which options exist** for its own fold. Its own selection never uses its held-out chips, and any two tuning sets
  share at least about 70% of their chips, so the effect is expected to be small, but it is not zero.
- **Cost bound:** one M2 stage-2 sweep per option is about 65 min serial (16 configurations x 446 chips x 0.55 s), 33 min at the
  measured 2x parallel speedup; one M1 sweep (k = 2 only) about 5 min serial. With at most 6 options per variant, stage 2
  is bounded by about **3.6 h at 2x** (plain and guarded variants sharing their options) up to about **7 h at 2x** (12
  distinct options per method); at an unmeasured 4x, about 1.8 h to 3.5 h. The actual estimate, from the real union, is
  reported before stage 2 starts.

## Amendment 7 (2026-09-20, after Stage 1 and BEFORE any re-ranking under it): the selection criterion is amended

### A7.1 Why, stated plainly

The criterion declared before tuning (section 6: mean per-chip flood-only IoU over tuning chips that have flood) **cannot reward the abstention guard**, because flood-free
chips do not enter it. **Stage 1 then showed exactly that** (A6.5): the guarded variants scored lower than their plain versions in 12 of 12 tuning sets for all four pairs,
and every guarded winner sat at the most permissive ceiling. **That weakness was documented before tuning began** (section 6, "Selection rule": "flood-free tuning chips
do not enter this criterion, so over-prediction there is only visible in the reported false-positive rate"). The amendment is nevertheless **post hoc with respect to that observation**: the project
owner and I had seen the Stage 1 rankings under the declared criterion when it was chosen. No re-ranking under the new criterion existed when this section was written.

### A7.2 The amended criterion (primary), exactly

For a candidate configuration and a tuning set S (the set's tuning chips, **all** of them, with or without flood):

  J(S) = sum over chips c in S of TP_c / sum over chips c in S of (TP_c + FP_c + FN_c),

with TP, FP, FN the **flood-only** counts (evaluation domain of section 1, JRC-masked, NaN and unlabelled pixels ignored). It is **pooled flood-only IoU over all tuning chips**.
A flood-free chip has TP = FN = 0, so it contributes only its false positives to the denominator; a chip with an empty domain contributes zero counts. A guard that abstains on a flood-free chip
therefore removes that chip's false positives from the denominator and can raise J. It applies to **every variant, plain and guarded** (B1, B2 VV/VH, M1, M2 and their guarded versions), and to the
preprocessing-option ranking of every stage. **Tie-breaks:** the declared ones are kept; the earlier "higher pooled IoU" tie-break is now the criterion itself, so an exact tie goes to the earlier candidate
in config order (thresholds ascending, ceilings in list order, options in config order). **How this differs from what was asked: it does not.** One property to keep in mind: pooling weights chips
by pixels, so chips with large flood areas or large false-alarm volumes dominate and the many small-flood chips count little. That is the reason both pooled and per-chip results continue to be reported.

### A7.3 The declared criterion becomes a sensitivity analysis

The declared criterion (mean per-chip flood-only IoU over tuning chips with flood, tie-breaks pooled IoU then config order) is kept as the **sensitivity criterion**. The **whole search is also run under it**
(the same count cache, so no extra clustering; separate rankings, unions, stage-2/3 selections, frozen configurations and held-out scores) and its results are **reported alongside the primary ones**. Selection is one
thing and reporting another: **both pooled and mean-per-chip held-out scores are reported for both criteria's configurations.** The reason given in A2.2 for making the mean per-chip IoU the headline
("it is the selection criterion") no longer holds; which score is the headline is left to the project owner (my suggestion: pooled, to match selection).

### A7.4 Re-applying the grid-edge rule (A2.5) under the amended criterion

The Stage 1 counts are re-used, so re-ranking costs nothing. The rule is then applied per criterion, per tuning set and per variant, with only the extensions that still trigger executed:

  once for all chips (about 21 minutes per level on 4 workers) and shared by both criteria; a (set, variant) whose winner is not at the edge does not get the extended options. Options absent from a set's ranking count as rank (length + 1) in the
  union's mean-rank tie-break (A5.3).

- **Exactness check (declared before running):** the derived counts must equal the stored counts for the three original ceilings (-18, -15, -12) for every unit and family; the run stops if any differs.

## Amendment 15 (2026-09-29, Accra: EXPLORATORY DIAGNOSTIC, not a frozen method, declared before running)

**Every output of this amendment is labelled `EXPLORATORY DIAGNOSTIC, UNVALIDATED`** in its file and
table headers -- distinct from the `UNVALIDATED` label used for the frozen-method outputs (A12-A13).
This is not a new method, is not retuned, does not touch `accra_pooled.yaml` or any frozen
configuration, and supports no conclusion about actual flooding.

### A15.1 Rationale (owner's, recorded)

Published SAR literature describes urban flooded pixels appearing **brighter**, not darker, because of
double-bounce scattering between floodwater and adjacent building walls -- the opposite sign from the
"darkest cluster = water" rule the whole frozen pipeline uses. Checked before writing this down:

- **Mason, D.C., Dance, S.L., Cloke, H.L. (2021)**, "Floodwater detection in urban areas using
  Sentinel-1 and WorldDEM data", *Journal of Applied Remote Sensing*, 15(3):032003,
  doi:10.1117/1.JRS.15.032003 -- **confirmed real** (DOI resolves, abstract corroborated by an
  independent Reading University repository page and a SPIE listing, both found and read via search).
  The paper's own method "searches for increased SAR backscatter in the post-flood image due to double
  scattering between water... and adjacent buildings." **I could not read the full text**: both the
  Reading repository PDF (blocked by an anti-bot page) and the SPIE PDF (returned empty) refused access,
  so no specific dB magnitude from this paper is used below.
- **Chini et al.**: a real body of work confirmed via search (their urban flood approach, described
  consistently across multiple independent sources, integrates histogram thresholding and region growing
  to map double-bounce-producing objects, later combined with InSAR coherence). No single Chini et al.
  paper was pinned down by DOI, so none is cited by year here.
- **"Li & Yu review"**: **I could not confirm a specific paper matching this exact author pairing.**
  Two 2024 SAR-urban-flood review papers turned up in search (Zhao, Li, Li, Matgen & Chini, "Urban
  Flood Mapping Using Satellite Synthetic Aperture Radar Data: A Review..."; and a separate MDPI
  *Remote Sensing* review, "Flood Detection with SAR: A Review of Techniques and Datasets"), but
  neither is a clean match to "Li & Yu", so **this citation is not used** rather than guessed at.
- **The qualitative mechanism itself (double-bounce brightening of flooded urban pixels) is
  well-corroborated** across the sources above, independent of the citation-matching problems. That is
  the only claim relied on here.

### A15.2 Thresholds, fixed before any result is looked at

**No specific dB magnitude could be extracted from the literature despite the attempts above**, so the
three thresholds below are declared from general SAR change-detection convention and radiometric
reasoning, not from a number quoted in a paper -- stated as such, not as a literature-sourced figure:

- **+3 dB**: a conventional minimal-significance cut in SAR change detection, roughly the scale of
  typical scene-to-scene radiometric/speckle fluctuation for GRD data; below this, a pixel's brightening
  is not distinguishable from ordinary noise.
- **+6 dB**: double the minimal threshold -- a harder-to-attribute-to-noise-alone signal.
- **+10 dB**: an order-of-magnitude increase in linear backscatter power: a conservative
  "unambiguously strong" cut, chosen because double-bounce returns are qualitatively described in the
  literature as very bright, not because a specific paper reports this number.

### A15.3 Method

1. `delta_VV = VV(2020-06-09) - VV(2020-06-03)`, dB, pixel by pixel, from the **already-downloaded raw
   VV rasters** (`data/accra/s1_*.tif`) -- no new imagery pulled, no clip/median filtering applied (a
   deliberately simple, unfiltered difference, per the owner's instruction; not the frozen pipeline's
   preprocessing).
2. Domain: both images' `image_valid_mask` (finite VV and VH, same function as everywhere else,
   `src/io.py`), AND NOT permanent water (JRC GSW occurrence >= 50%, same mask as A12.4(b)).
3. Reported for the full Odaw AOI and separately for each of the three sub-AOI pieces (core, kaneshie,
   darkuman_clipped): the distribution of `delta_VV` (min, max, mean, median, 5th/25th/75th/95th
   percentiles); area (ha) above each of the three thresholds; and overlap with M2g's 9 June flagged
   (darkened) pixels on the same domain, recomputed from the frozen `accra_pooled` M2g configuration
   (deterministic, same seed, not retuned) since the prediction array itself was not saved earlier.
4. **A brightness increase is reported as CONSISTENT WITH, not proof of, flooding** -- ordinary
   day-to-day radar variation, soil moisture change, incidence-angle effects, or other surface change
   could produce the same signature, and there is no ground truth to check against either reading. No
   conclusion about actual flooding on 8-9 June is drawn from this diagnostic.

**A19-R2.5 UN-SPIDER ratio rule, as a labelled sensitivity variant (headline unchanged: -3 dB, assumption).**
Reference: UN-SPIDER Knowledge Portal (UN Office for Outer Space Affairs), "Step-by-Step: Recommended Practice: Flood
Mapping and Damage Assessment Using Sentinel-1 SAR Data in Google Earth Engine",
https://un-spider.org/advisory-support/recommended-practices/recommended-practice-google-earth-engine-flood-mapping/step-by-step
(page read 2026-10-19; no date or version shown on the page). What the page says, quoted: "the after-flood mosaic is
divided by the before-flood mosaic"; "The predefined threshold of 1.25 is applied assigning 1 to all values greater than
1.25 and 0 to all values less than 1.25"; "The threshold of 1.25 has been selected through trial and error"; preprocessing
includes "Conversion of the backscatter coefficient (σ°) into decibels (dB)"; "'VH' is widely suggested for flood mapping"
but users can choose VH or VV; smoothing of 50 m circles; masks for permanent water, slope above 5% and connected pixels (eight
or fewer neighbours).
- **Rule (labelled `UN-SPIDER ratio 1.25 sensitivity`):** `ratio = V_dB(second date) / V_dB(first date)` per pixel, flood
  if `ratio > 1.25`, with V the median-3 filtered backscatter in dB, for **VH** (the page's suggested polarization) and,
  separately, **VV** (to match the headline rule). Same pairs, areas, JRC exclusion, domain and event-minus-control reporting
  as A19.3-A19.5, including the same-satellite pairs. No guard.
- **Reading I could not verify:** the page does not state whether the division uses dB or linear values; the script file
  it links (`/sites/default/files/Code_GEE_flood_mapping.txt`) returned HTTP 403 to both the fetch tool and curl, so I
  could not read it. I adopt the literal sequence on the page (convert to dB, then divide), i.e. the dB values are divided.
  My reasoning that this is the intended reading (estimate, unverified): dB values are negative, so a post-event value more
  negative than the pre-event one gives a ratio above 1 (darkening, the open-water flood direction), whereas a linear
  after/before ratio above 1.25 would flag brightening. **No linear-ratio version is run and no other reading is substituted.**
- **Deviations from the UN-SPIDER pipeline (stated, not hidden):** the median-3 filter replaces its 50 m focal smoothing; its

  rule only, not a reproduction of the UN-SPIDER workflow, and the CSV label says so.
- **Interpretation limit:** the 1.25 is a trial-and-error value with no source, as the page itself says. It is a second
  unsourced threshold next to -3 dB, not independent evidence for either.

### A20.2 Rule: A10.2, unchanged and not relaxed

A candidate is accepted only if **both** hold:
- **(a)** at least one Sentinel-1 IW GRD acquisition over the Odaw AOI **within 24 h after** the reported peak, on **any** orbit (same-orbit
  baselines are not part of screening). Fixed reading: PASS if some scene's start time `t` satisfies `peak < t <= peak + 24 h`.
- **(b)** an independent reference: a Copernicus EMS Rapid Mapping activation or a UNOSAT map, OR a Dartmouth Flood Observatory record, OR a
  Sentinel-2 scene within 3 days whose **AOI-clipped** cloud fraction is below 20%, as in A11.2: `COPERNICUS/S2_SR_HARMONIZED`, band `SCL`,
  classes 3, 8, 9, 10, `ee.Reducer.mean()` over the Odaw AOI polygon at 20 m, never the tile-wide `CLOUDY_PIXEL_PERCENTAGE`. Fixed reading of "within 3 days":
  scene time within +/- 3 days (72 h) of the assumed peak, both sides, with the offset reported for every scene. As in A12.2/A14.3, the cloud criterion
  is only a **necessary** condition: no imagery is pulled, so the "visible surface water consistent with flooding" visual check is **not** done.

  with its own publication date and year. If a **second named source with a clock time** is found, it is quoted too; **I do not choose between sources**: rule (a)
  is reported for each peak.
- **Bounding window:** rule (a) is also reported for the peak at each end of 2020-10-10T00:00 and 2020-10-10T12:00 UTC.
- **Verdict convention, fixed now:** the headline PASS or FAIL for rule (a) is the one at the **assumed peak (06:00 UTC)**. Verdicts at the window ends and at

## Amendment 22 (2026-10-20, **POST-HOC**, Kotoka ISD precipitation reports 7 to 11 June 2020; the owner's option (b) with changes; written BEFORE the pull; no imagery, no method)

Tags: **[M]** measured; **[A]** rule or assumption; **[E]** estimate or reasoning. POST-HOC and descriptive only: chosen after A21's stop rule fired on 8 June (GSOD flag I). No rule is changed. Nothing here is validation.

### A22.1 What is pulled

- NOAA ISD for **654720-99999 (KOTOKA INTL)**, year 2020, NCEI's documented layouts, one attempt each: first `https://www.ncei.noaa.gov/data/global-hourly/access/2020/65472099999.csv`; if that fails, the same ISD data in
  `https://www.ncei.noaa.gov/pub/data/noaa/2020/654720-99999-2020.gz`. The file used is stated in the output. Observation times are UTC as ISD gives them.
- Window: observation times **2020-06-07 00:00:00 to 2020-06-11 23:59:59 UTC**. Every record in it is kept, whatever the report type (synoptic, hourly METAR and so on).
- **Precipitation groups reported:** every non-empty group among `AA1`-`AA4` (liquid-precipitation accumulation: period in hours, depth, condition code, quality code), `AO1`-`AO4` (the sub-hourly version, period in minutes),
  `AP1`-`AP4`, `AH1`-`AH6`, `AI1`-`AI6`. **Each group is given exactly as it appears (the raw string)**, with its observation time, report type and source flag. Decoding is limited to the unit conversion for `AA`: period in hours and
  depth = the stored value / 10 in mm; `9999` is shown as missing; `AO`, `AP`, `AH`, `AI` are given raw and not decoded unless the same simple layout applies and is read from NOAA's ISD format document at run time. **Quality and condition codes are
  shown verbatim**; their meanings are quoted from NOAA's ISD format document only if I can retrieve and read it at run time, otherwise left as codes with "meaning not read".
- **No merging, no inference, no infilling.** No amount is added to another, split, or apportioned in the table.

### A22.2 Which observation each GSOD daily total corresponds to

For 8, 9, 10 and 11 June, the GSOD `PRCP` (A21.2 file) is matched to ISD reports by this rule fixed now: among `AA` groups whose observation time falls on that UTC date, those whose depth in inches (mm / 25.4, rounded to 0.01)
equals the GSOD value; **only if exactly one `AA` group matches** is it named as the source, with its observation time and its accumulation window `[observation time - period, observation time]` UTC. If none or more than one matches, or GSOD flags the day `I`
(no precipitation data), I say "not determinable" and name whatever `AA` groups exist that day, without guessing. The GSOD flag and NOAA's definition are quoted beside it.

### A22.3 The table, with three markers

One table in time order of all reports in the window, with marker rows inserted at their times: **(1)** the reported storm window **2020-06-08 22:00 to 2020-06-09 06:00 UTC** (A12.1), **(2)** the Sentinel-1 pass **2020-06-09 18:18:05 UTC**,
**(3)** the IMERG heaviest rain **2020-06-10 15:30 to 18:00 UTC** (A19-R4). A report is also tagged with whether its accumulation window overlaps each marker.

### A22.4 The only interpretation allowed: rain at the gauge before the pass, between the pass and 10 June 12:00, and after 10 June 12:00

Segments: **(i) before the pass:** 2020-06-07 00:00 to 2020-06-09 18:18:05; **(ii) pass to 10 June 12:00:** 2020-06-09 18:18:05 to 2020-06-10 12:00; **(iii) after 10 June 12:00:** 2020-06-10 12:00 to 2020-06-12 00:00 (end of the pulled period). Because
the reports are accumulations over their own windows and I may not split them:
- a segment's amount is stated **only** from reports whose whole accumulation window lies inside the segment, taking the shortest-period `AA` groups available, provided those windows are **contiguous and non-overlapping across the whole segment**; then the amount is their sum **as given** (a sum of reported
  values, not an inference about unreported time);
- a report whose window **straddles** a segment boundary (the pass at 18:18:05, or 10 June 12:00) is **shown separately as straddling** and counted in neither neighbouring segment;
- if the windows do not tile a segment (gaps, missing groups, overlapping periods that cannot be separated), that segment is reported as **"not determinable from the reports as given"**, with the gaps listed, and not filled.
No other statement about the gauge is made: no comparison with IMERG or with the reports of flooding, no statement about the 8-9 June storm beyond which reports overlap its window.

### A22.5 Stop rule

If the ISD file cannot be retrieved, or has **no record at all** in 2020-06-07 to 2020-06-11, or has **no precipitation group** of the types listed in A22.1 anywhere in the window, I say "hourly or synoptic records are missing" and **stop** without a table. Partial gaps are reported, not a stop.
